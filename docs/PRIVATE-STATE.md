# Private-state candidate

Task #6 adds a local, synthetic-qualified private storage/API path on the existing account and SQLite seams. It has not been deployed to the running account preview. The installed preview still uses application release `9d57d26`; pushing this source does not update that root-pinned service. No real personal content or runtime credentials were used to develop or test this candidate.

## Boundary and storage

In account mode, every private request repeats the same Origin, cookie, invitation and current-session validation used by `/api/session`. Its companion scope comes only from the server's provisioner. A client cannot select an owner, principal, companion, runtime or credential namespace. Missing and foreign records/threads return the same fixed 404. Revoked sessions cannot access the next protected request.

The ledger uses additive, versioned tables inside the existing private `bootstrap.sqlite`, plus an independent initialization marker in `bootstrap_record`. Existing companion identities remain unchanged. Missing, altered or shadowed schemas, unexpected attached triggers/indexes, inconsistent sequence heads and corrupted replay receipts refuse rather than resetting data. Initialization and mutations are atomic SQLite transactions.

On POSIX, the data directory must be owned by the process with mode0700. Database and retained SQLite sidecars must be regular single-link files owned by that process with mode0600 before SQLite opens them. Directory links, unsafe ancestors and unsafe retained files refuse instead of being silently repaired. Root-owned sticky temporary ancestors are allowed for isolated tests. Windows synthetic tests do not prove private ACL isolation.

The shared host administrator is trusted. Mode bits and API owner checks do not conceal files from that administrator or separate users sharing the service's Unix identity. In particular, a read-only home mount does not hide same-UID credential files. Actual owner-controlled runtime placement, credential homes, registry/binding and runtime-side checks remain unqualified #7/#8 obligations; unavailable routes are not positive proof of those capabilities.

## HTTP contract

Only account mode accepts `POST /api/private/state`. Requests need the current secure platform cookie, the exact configured Origin and `Content-Type: application/json`. Body limit64KiB, deadline3seconds. Responses use `Cache-Control: no-store`; errors contain fixed codes/messages and no values, paths or identifiers. Default/demo modes cannot expose this path through query parameters or forwarded headers. The running staging proxy still has its old1KiB request limit; changing that proxy or activating private writes requires its concrete deployment gate.

Exact request shapes:

```json
{"action":"read","id":"<returned-record-UUID>"}
{"action":"list","kind":"thread","limit":50}
{"action":"list","kind":"message","threadId":"<owned-thread-UUID>","cursor":"<returned-list-cursor>","limit":50}
{"action":"changes","cursor":"<returned-changes-checkpoint>","limit":50}
{"action":"mutate","mutation":{"requestId":"thread-1","op":"create","kind":"thread","expectedVersion":0,"value":{"title":"Synthetic example"}}}
{"action":"mutate","mutation":{"requestId":"message-1","op":"create","kind":"message","threadId":"<owned-thread-UUID>","expectedVersion":0,"value":{"text":"Synthetic example"}}}
{"action":"mutate","mutation":{"requestId":"edit-1","op":"update","id":"<owned-record-UUID>","expectedVersion":1,"value":{"text":"Revised synthetic example"}}}
{"action":"mutate","mutation":{"requestId":"remove-1","op":"remove","id":"<owned-record-UUID>","expectedVersion":2}}
```

`cursor`, `limit` and non-message `threadId` omission rules follow the examples: list always requires kind, message list/create requires an active owned thread, other kinds forbid threadId, and changes can start without a cursor. Page size is at most50. Explicit null cursors/limits and unknown fields are rejected.

Kinds are `thread`, `message`, `goal`, `permission`, `decision`, `memory`, `preference`, `personality`, `work`, and `watch`. These are private stored data, not permission grants, trusted assistant output or dispatch authority. Every message value is owner-submitted data. Later feature layers must validate actual goal/permission semantics and runtime provenance before acting. No Board exporter, runtime connector or tool execution is implemented here.

Values are plain finite JSON, at most16KiB serialized and64 nested containers; IDs are generated by the server. Request keys contain1–80 ASCII letters/digits/`.`/`_`/`-`. Creates require expectedVersion0; update/remove require the current positive version and cannot move kind/thread ownership. Conflicts return409, invalid requests/cursors400, foreign/missing records404 and unavailable/corrupted storage503.

## Ordering, paging and deletion

Each committed mutation allocates one increasing sequence per companion. Version comparison, record/event changes and request-key receipt commit together. The same request key and canonical operation returns the original metadata result without a second commit; changing the operation conflicts. Fingerprints and replay metadata are HMAC-bound with a private persisted owner key. No old value is retained in replay receipts or change events.

List cursors bind owner, kind, thread and the initial creation watermark. Later creations are excluded from the remaining list pages. Current values may advance during paging; use the list's initial changes checkpoint to catch up afterward. Changed versions invalidate cached records. Changes pages advance only through returned events; do not skip to an unseen final head. Cursors survive restart and reject owner/purpose/filter substitution, tampering and impossible positions.

Changes are ordered metadata invalidations, not a replay of historical private values. Removing a thread emits one parent deletion event and atomically clears/tombstones its messages. Clients must purge that thread's cached children. Read/list hide tombstones, and old request retries cannot resurrect content. This is logical deletion and retained metadata; secure erasure of backups, historical copies and administrator access is not claimed. Full forgetting controls remain a later feature.

## Evidence limits

Synthetic two-owner/two-device HTTP tests cover authentication/revocation, restart, ordered concurrent commits, idempotency/CAS, cursor substitution/paging and deletion. Separate real-filesystem tests cover POSIX ownership/modes and sidecars; platform skips are reported. No real account-session data, private conversation or provider credentials enter tests, Git or Board payloads.

These proofs qualify the local private-state implementation. They do not qualify actual personal-runtime routing, credentials, registry/rebinding, event producers, inference, live private-state deployment or a full companion pilot. The dated task #6 runtime requirements must retain their own evidence; any split into #7/#8 needs explicit owner acceptance before #6 is called fully complete.
